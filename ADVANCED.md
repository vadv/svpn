# SVPN: расширенные настройки

Базовая установка с одним сервером описана в [README.md](README.md). Здесь —
несколько VPS, sticky-политика, базы GeoIP, hooks, транспорт, systemd и детали
`svpn setup`. Конфигурационный файл — HCL.

## Несколько VPS и sticky

Полный пример: два VPS, `sticky`-блоки по именам, странам и ASN, локальный
egress для RU/BY и распределение по весам. Замените адреса серверов и путь
к ключу.

```hcl
# vpn.hcl
ssh {
  user       = "root"
  identity   = "/полный/путь/к/ключу"
  port       = 22
  remote_bin = "/usr/local/bin/svpn"
}

transport {
  mimic      = ["ssh"]
  tcp_port   = 41020  # фиксированный TCP-fallback; обязателен при mimic = ["ssh"] без UDP
  udp_ports  = "60000-60009"
}

geo {
  db = "/etc/svpn/asn.csv"         # для asn-селекторов и strategy = "sticky-asn"
}

country {
  db = "/etc/svpn/country.csv"     # для countries-селекторов
}

fallback_sticky {
  strategy = "sticky-asn"          # как пул обслуживает трафик вне sticky-блоков
  mode = "hashed"                  # default; balanced — по числу живых ASN / вес
  state    = "/etc/svpn/exits.json"
}

server "nl" {
  address = "203.0.113.10"
  weight  = 3
}

server "de" {
  address = "198.51.100.20"
  weight  = 1
}

# Порядок блоков = приоритет: первое совпадение выигрывает.
sticky "claude" {
  names = ["claude.ai", "anthropic.com"]
  via   = ["nl"]                   # один элемент = жёсткая привязка
  every = "5m"                     # перерезолв имён (min 5s, default 300s)
}

sticky "eu" {
  countries = ["NL", "DE"]
  via       = ["de", "nl"]         # rendezvous: стабильно + failover
}

sticky "home" {
  countries = ["RU", "BY"]
  via       = local                # локальный egress, мимо VPN
}
```

## Как выбирается путь

Маршрутизация — ровно два механизма:

1. **sticky-блоки** — упорядоченный first-match: адрес назначения проверяется
   по блокам сверху вниз, побеждает первое совпадение. Что совпало:
   - `via = ["…"]` — вся группа закреплена за одним сервером из списка
     (rendezvous по весам; отказ сервера переносит группу на следующего,
     возврат не возвращает группу обратно — snap-back запрещён);
   - `via = local` — пакеты уходят через локальный сервер SVPN и физический
     uplink (сайт видит ваш домашний IP). Базы для этого не нужны, если
     селектор `names` или `ips`.
2. **fallback_sticky** — трафик, не пойманный ни одним блоком:
   `balance` (взвешенно по потокам) или `sticky-asn` (группы ASN со
   стабильным владельцем; требует `geo.db`).

| Назначение из примера | Путь |
|---|---|
| IP, в которые резолвится claude.ai / anthropic.com | Всегда через `nl` |
| Адреса NL и DE | Один владелец из `de`+`nl`, failover между ними |
| Адреса RU и BY | Локальный egress, мимо VPN |
| Всё остальное | `sticky-asn`: группа ASN → один владелец из всего пула |

`weight` — доля групп, которыми владеет сервер: веса 3 и 1 дают примерное
распределение 3:1. Веса влияют на выбор владельца, а не на каждый пакет.

### `via = local`: как устроен локальный egress

Второй TUN не создаётся. Локальный egress — прокси внутри `serve`: TCP- и
UDP-потоки терминируются userspace-стеком, ICMP echo — одним RAW-сокетом
(identifier переписывается на proxy-id). Исходящие сокеты привязаны к
WAN-интерфейсу (`SO_BINDTODEVICE`), интерфейс выбирается автоматически по
таблице маршрутов; NAT и nftables на клиенте не нужны. Серверные hooks на
VPS работают как раньше.

Принятые решения:

- только IPv4; ICMP ограничен echo (ошибки type 3/11/12 не транслируются);
- лимиты на одновременные TCP/UDP/ping-потоки: превышение — дроп со
  счётчиком; отказ TCP admission закрывает поток событием `Closed`, отказ
  connect и обрыв relay возвращают клиенту RST;
- UDP и ping принимают ответ с любого адреса хоста (weak-host);
- продакшн — Linux (`SO_BINDTODEVICE`, raw-сокет); без WAN-устройства
  (тестовый вход) egress-потоки дропаются.

### Селекторы и резолвер

- Ровно один селектор на блок: `names`, `countries`, `ips` или `asn` — все
  списки; группа = объединение элементов.
- `names`: SVPN сам эпизодически резолвит имена системным резолвером —
  первый резолв сразу при старте, далее каждые `every`. До первого резолва
  адреса идут по fallback. IP, пропавший из двух подряд резолвов, вымывается
  из группы (защита от пересдачи адресов CDN). Ошибка резолва сохраняет
  прежний набор IP.
- `ips`: точные адреса и CIDR; host-биты в CIDR должны быть нулевыми.
- `countries` требует `country.db`, `asn` и `strategy = "sticky-asn"` —
  `geo.db`.
- Дублировать селектор в двух блоках нельзя: второй был бы мёртвым конфигом.

Владельцы sticky-групп и ASN-групп персистятся в одном `state`-файле и
переживают рестарт: перезапуск во время сбоя не дёргает группы обратно.

## DNS за выходом

По умолчанию SVPN не занимается DNS. Клиент спрашивает свой резолвер и получает
адрес, а SVPN только выбирает выход по этому адресу. Поэтому CDN и сервисы с
геопривязкой могут отдать клиенту адреса для страны резолвера, а не для страны
выхода.

Чтобы DNS разрешался на выходе, добавьте блок:

```hcl
dns {
  mode  = "exit"
  local = ["77.88.8.8"]   # необязательно
}
```

Перед включением обновите `svpn` на всех серверах: старая версия сервера
закрывает соединение, получив DNS-запрос от клиента.

Что происходит с запросом:

1. Клиент отправляет DNS-запрос (UDP, порт 53) в туннель. SVPN перехватывает
   его и отвечает сам, от имени того резолвера, который указал клиент.
2. Для имени из sticky-блока `names` SVPN отправляет запрос через выход этого
   блока. Для остальных имён — через выход по умолчанию. Первый запрос для
   нового имени всегда идёт через VPN, а не через провайдера.
3. Получив ответ, SVPN смотрит, через какой выход пойдёт трафик к первому
   адресу из ответа. Если это другой выход, SVPN повторяет запрос через него и
   отдаёт клиенту второй ответ.
4. Ответ сохраняется в кэше. Пока не истёк его TTL, повторные запросы этого
   имени SVPN отвечает сам.

Где разрешаются имена:

| Выход | Кто разрешает |
| --- | --- |
| VPN-сервер | `svpn server` через системные резолверы VPS. Запрос и ответ передаются внутри SSH-соединения |
| `via = local` | SVPN на клиенте. Резолверы берутся из `local` или из системы (см. ниже) |

`local` задаёт резолверы для `via = local`. Без `local` SVPN берёт `nameserver`
из `/etc/resolv.conf`, а на OpenWrt — из `/tmp/resolv.conf.d/resolv.conf.auto`.
Адреса 127.0.0.0/8 при этом пропускаются, чтобы не зациклиться с dnsmasq.
Запросы уходят через WAN-интерфейс.

Кэш:

- Ответ хранится до конца TTL. Для отрицательных ответов (имя не найдено) срок
  берётся из SOA-записи, по RFC 2308. Когда SVPN отдаёт ответ из кэша, он
  уменьшает TTL на время хранения.
- Если выход не ответил (таймаут, обрыв линка, SERVFAIL от резолвера), SVPN
  отдаёт клиенту последний сохранённый ответ, даже если его TTL уже истёк. TTL
  в таком ответе не больше 30 секунд. Если сохранённого ответа нет, клиент
  получает SERVFAIL.
- После ошибки SVPN 5 секунд не отправляет наружу запросы того же имени.
- В кэше не больше 4096 записей. Когда место кончается, первыми удаляются
  записи с самым маленьким оставшимся TTL.

Чтобы запросы клиентов попали в туннель, dnsmasq на роутере должен отправлять
их через адрес туннеля:

```
list server '1.1.1.1@10.77.0.2'
```

`10.77.0.2` — адрес туннеля, замените на свой. Вместо `1.1.1.1` можно указать
любой адрес: SVPN ответит вместо него. Другие строки `server` в настройках
dnsmasq нужно убрать, иначе dnsmasq будет отправлять запросы и туда.

Ограничения:

- Перехватывается только UDP/53. DNS поверх TCP, DoT и DoH проходят как
  обычный трафик.
- Если ответ не помещается в MTU туннеля, SVPN отдаёт клиенту усечённый ответ
  (флаг TC). Дальше клиент запрашивает полный ответ по TCP, как обычно.
- Адреса для sticky-блоков `names` SVPN по-прежнему узнаёт через системный
  резолвер.
- IPv6 не туннелируется. Запросы AAAA обрабатываются так же, как остальные.
- Адреса серверов SVPN разрешает через системный резолвер, поэтому DNS на
  роутере должен работать и без туннеля. Другой вариант — указать в `server`
  адреса, а не имена.
- Пока нет ни одного готового линка, запросы идут как обычно.
- Счётчики DNS есть в периодическом отчёте: `dns: queries | cache | stale | moved | failed`.

## Базы стран и ASN

Обе базы нужны на **клиенте**, а не на VPS. Каталог и файлы доступны только
root:

```bash
sudo install -d -m 700 /etc/svpn
YEAR_MONTH=$(date +%Y-%m)

curl -fL "https://github.com/sapics/ip-location-db/releases/download/latest/server-country-ipv4.csv" -o /tmp/country.csv
sudo install -m 600 /tmp/country.csv /etc/svpn/country.csv

curl -fL "https://download.db-ip.com/free/dbip-asn-lite-${YEAR_MONTH}.csv.gz" -o /tmp/asn.csv.gz
gzip -dc /tmp/asn.csv.gz | sudo tee /etc/svpn/asn.csv >/dev/null
sudo chmod 600 /etc/svpn/country.csv /etc/svpn/asn.csv
```

База стран — `server-country` из
[ip-location-db](https://github.com/sapics/ip-location-db) (статистика
регистратур, BGP и geofeed'ы операторов, обновляется ежедневно) — определяет
страну назначения (нужна `countries`-селекторам); ASN Lite (DB-IP, ежемесячно)
— сеть (нужна `asn`-селекторами и `sticky-asn`). SVPN загружает CSV
при запуске; при обновлении вручную перезапустите сервис (`sudo systemctl
restart svpn`) — или доверьте обновление фоновому job'у (следующий раздел):
он меняет файл и svpn перечитывает таблицу сам.

Больше ничего вручную: автообновление делают фоновые job'ы (следующий раздел).

## Фоновые job'ы

`job`-блоки — прозрачный планировщик по образцу systemd: svpn запускает ваш
скрипт по расписанию и не интерпретирует результат. Для баз — один флаг,
без всяких блоков:

```hcl
geo     { db = "/etc/svpn/asn.csv";     auto_job_update = true }
country { db = "/etc/svpn/country.csv"; auto_job_update = true }
```

Встроенный job уже умеет всё: проверяет свежесть (`run_if`), качает во
временный файл (безопасно при параллельных запусках), проверяет размер и
ставит базу атомарно. svpn подхватывает её **вживую, без перезапуска**.
Для своего зеркала или графика возьмите блок-образец
`svpn example job-geo-update` — это тот же встроенный job, выведенный как
конфиг (и выключите `auto_job_update`, чтобы labels не столкнулись):

```hcl
job "geo-update" {
  every   = "1h"     # интервал попыток; первая — сразу при старте
  timeout = "10m"    # SIGKILL-граница (default 10m)
  run_if  = <<EOF    # exit 0 = «есть работа»; не-0 = дешёвый пропуск
    …проверка свежести…
  EOF
  run     = <<EOF    # /bin/sh -c, как hooks
    …сам скрипт…
  EOF
  reload  = ["geo"]  # после exit 0: перечитать таблицы (geo / country)
}
```

Семантика:

- **Попытки**: старт приложения и далее каждые `every`. Бежащий job не
  складывается — следующая попытка ждёт его. Провал — лог и счётчики
  (`jobs: runs / failures / timeouts` в отчёте), ретрай по расписанию.
- **Degraded-старт**: база отсутствует, но job с `reload = ["geo"]` есть —
  старт не блокируется: sticky-asn работает как balance, в логе
  `vpn: degraded start — geo database missing, job … fetching it`, в каждом
  отчёте `geo: missing (job …)`, пока job не принесёт базу.
- **Reload**: файл не спарсился — в памяти остаётся предыдущая таблица, диск
  не трогаем: содержимое файла — ответственность вашего скрипта.
- **Окружение** (не хардкодите пути):

| переменная | значение |
|---|---|
| `SVPN_OS` | `linux` / `macos` / `openwrt` |
| `SVPN_GEO_DB`, `SVPN_COUNTRY_DB` | пути баз из конфига |
| `SVPN_CONFIG_DIR` | директория конфиг-файла |
| `SVPN_JOB` | label job'а |

- **Вывод**: хвост (~16 строк) в лог с префиксом `job[name]:` — скрипты могут
  печатать секреты, полный вывод не хранится.
- **Сон/суспенд растягивает интервалы** — таймеры монотонные, как у systemd.

Ручное управление:

```bash
svpn job list --config vpn.hcl          # какие job'ы объявлены
svpn job run geo-update --config vpn.hcl  # выполнить сейчас, вывод на экран,
                                          # код выхода = коду job'а (124 = таймаут)
```

`superseded: scripts/update-asn-db.sh — заменён шаблоном
svpn example job-geo-update; скрипт удалён.`

## Server hooks

`server_up` и `server_down` выполняются на VPS, а также у локального egress
на клиенте. Если поля не заданы, `serve` выполняет встроенные
`scripts/server-up` и `scripts/server-down` текущего бинарника.

Глобальные умолания задаются в блоке `hooks`, для конкретного сервера —
внутри его блока (многострочные команды удобно писать heredoc'ом):

```hcl
hooks {
  server_up = <<EOF
sysctl -w net.ipv4.ip_forward=1
EOF
}

server "de" {
  address    = "198.51.100.20"
  server_up = "echo свой вариант только для этого сервера"
}
```

Чтобы отредактировать встроенный скрипт, посмотрите его, сохраните,
измените и укажите в конфиге:

```bash
svpn example server-up > server-up
svpn example server-down > server-down
$EDITOR server-up server-down
```

Hooks получают переменные окружения:

- `SVPN_EVENT` — `up` или `down`;
- `SVPN_TUN_NAME` — имя TUN;
- `SVPN_TUN_ADDR` — адрес туннеля на этой стороне;
- `SVPN_PEER_ADDR` — адрес туннеля на другой стороне;
- `SVPN_SESSION_ID` — PID процесса.

Timeout — 10 секунд. Ошибка `up` не даёт поднять сессию, ошибка `down` только
пишется в лог.

## Клиентские hooks

В auto выполняются встроенные `scripts/client-up` и `scripts/client-down` из
текущего бинарника. Точный текст можно посмотреть до запуска:

```bash
svpn example client-up
svpn example client-down
```

Скрипт получает `SVPN_SERVER_ADDRS` и `SVPN_OS`, затем:

1. для каждого VPS добавляет `/32` host route через исходный путь;
2. добавляет `0.0.0.0/1` и `128.0.0.0/1` через TUN;
3. при `down` удаляет только маршруты этой сессии.

Ручной override — в блоке `hooks`: `up_command`/`down_command` (строка для
`/bin/sh -c`) или `up_script`/`down_script` (путь к исполняемому файлу).
Направления независимы: можно оставить автоматический up и задать свой down.
Явная команда отключает встроенный скрипт только в своём направлении.
Команды получают те же переменные, что и server hooks, timeout тот же —
10 секунд.

## Проверка SSH и host key

На клиенте должен быть закрытый ключ. Его открытая часть должна быть разрешена
на VPS. Используйте абсолютный путь к ключу (относительные пути в конфиге
считаются от директории конфиг-файла). Если ключ защищён passphrase,
загрузите его в `ssh-agent` заранее.

Без `host_key` SVPN использует TOFU и сохраняет fingerprint в своём
known-hosts файле. Для строгой проверки получите fingerprint у провайдера и
добавьте `host_key = "SHA256:..."` в блок сервера. Пустое значение не нужно.

## Транспорт

По умолчанию используется SSH camouflage и UDP. Если UDP заблокирован, задайте
`mimic = ["ssh"]` в блоке `transport`. Диапазон UDP-портов — строка
`udp_ports = "60000-60009"`.

`tcp_port` — фиксированный порт TCP-fallback. В auto он необязателен и по
умолчанию эфемерный, поэтому базовая настройка не требуется. Но при
`mimic = ["ssh"]` без UDP-стратегий он обязателен: TCP-only серверу нужен
известный порт. `mimic` и `tcp_port` можно задать отдельно для каждого
сервера в его блоке: разные VPS могут работать с разными масками.

## Автозапуск

```bash
sudo install -d -m 700 /etc/systemd/system
sudo tee /etc/systemd/system/svpn.service >/dev/null <<'EOF'
[Unit]
Description=SVPN
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/local/bin/svpn multi --config /etc/svpn/vpn.hcl
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now svpn
systemctl status svpn
journalctl -u svpn -f
```

Для одного сервера замените `multi` на запуск без подкоманды:
`ExecStart=/usr/local/bin/svpn --config /etc/svpn/vpn.hcl`.

## Подробности `svpn setup`

`svpn setup --config FILE` подготавливает каждый VPS из конфига: определяет
окружение, ставит недостающие проверенные пакеты (`curl`, `tar`, `gzip`, `awk`,
`ip`, `nft`, `sysctl`, CA-сертификаты), скачивает релиз SVPN с GitHub прямо на
VPS и устанавливает бинарник. Конфиг не изменяется; hook-файлы setup не
создаёт.

Поддерживаемые окружения: Debian/Ubuntu и Rocky/CentOS Stream (GNU libc) на
x86_64 и aarch64 с аппаратным AES. Вход по SSH — `root` или обычный пользователь с безпарольным
`sudo -n`; пароли и интерактивный sudo не поддерживаются. OpenWrt, Alpine и
musl команда не обслуживает.

Повторные запуски и версии:

- Перезаписывается только управляемый файл `/usr/local/bin/svpn`.
  Замена атомарна; отчёт честно показывает `partial` при частичной установке.
- Предпочитается версия клиента. Если её релиз или архив под платформу
  недоступны, выбирается последний стабильный релиз с совместимыми
  control/hook метаданными, и причина сообщается. Ошибка контрольной суммы —
  это ошибка, а не переход на другой релиз.
- Выбранная более старая версия может заменить установленную новую — это
  сообщается явно полем `downgrade=`.

После установки проверяются хеш, права и версия бинарника. Setup не запускает
SVPN и не выполняет хуки: команда не активирует маршруты, NAT, DNS и firewall,
не создаёт сервисы и не трогает локальный egress.

Хосты обрабатываются по порядку конфига; сбой одного не останавливает
остальные. Каждому хосту печатается строка
`SETUP host=… status=success|failed|partial|unknown|not-attempted` с выбранной
версией, полем `downgrade=` и списком `changed=`. Итоговый код отличен от нуля
при любом сбое. Прерывание (Ctrl+C, SIGTERM) останавливает новые хосты:
активный получает `unknown`, оставшиеся — `not-attempted`.

## Состояние и лимиты

В foreground смотрите строки `serving` и `local-exit: ready`. Для systemd
используйте `journalctl -u svpn -f`. Повторные запуски одинаковых конфигураций
занимают пары адресов из пула `10.77.0.0/16`. При конфликте проверьте занятые
адреса через `ip addr`.

### Режим автоматического sticky-ASN

`fallback_sticky.mode` (CLI: `--sticky-asn-mode`) действует только при
`strategy = "sticky-asn"`. Стратегия `balance` остаётся балансировкой по flow.

| Режим | Выбор нового ASN | После последнего flow |
|---|---|---|
| `hashed` (default) | Weighted rendezvous по ASN и весам Ready-серверов | Владелец остаётся в RAM до отказа или рестарта |
| `balanced` | Минимум «живые уникальные ASN / вес», при равенстве rendezvous | Привязка сразу исчезает; следующий flow делает новый выбор |

Closing/retained flow удерживает ASN до фактического удаления. 100 flow одного
ASN считаются одной группой; явные sticky-блоки в этот счётчик не входят и
сохраняют hashed-владельца внутри своего `via`. Неизвестный ASN — stateless
weighted rendezvous по IP. Geo reload не меняет принадлежность старого flow.

В обоих режимах открытые соединения не переносятся. Пока владелец Checking,
новые flow группы не выдаются резерву (очереди ожидания нет). После отказа
старые flow завершаются, новые выбирают Ready-выход. В hashed восстановление
прежнего сервера не вызывает snap-back, но следующий отказ может выбрать его
снова. В balanced восстановившийся сервер участвует в выборе новых групп.
Балансируются группы, не мегабиты или CPU; отдельного индекса истории нет.

TTL/sweep нет. В hashed карта содержит все встреченные ASN до рестарта;
это не обещание постоянного RSS. `fallback_sticky.state` принимается, но
игнорируется; `--exit-state` удалён. Файл `exit-state.json` больше не читается
и не пишется, существующий файл автоматически не удаляется.

## Веб-морда

Клиент (не сервер) умеет отдавать своё состояние в браузере. Включается
адресом на loopback — по умолчанию морды нет:

```bash
sudo -E svpn --server 203.0.113.10 --web-listen 127.0.0.1:8080
```

или в конфиге (запуск — только `svpn multi --config vpn.hcl`, без
клиентских флагов):

```hcl
dashboard {
  listen = "127.0.0.1:8080"
}
```

Что видно:

- Сводка: готовые серверы, RX/TX в Mbit/s, активные соединения и готовность
  local exit. `ready` означает готовность соединения, не проверку всего интернета.
- **Traffic** — один график внутреннего IP-трафика VPN. Это не весь WAN и не
  скорость local exit. Диапазон **5 min** страница измеряет сама: один сэмпл в
  секунду, каждый сервер — свой слой. Диапазоны час, сутки, неделя, месяц,
  вчера и свой период страница читает из базы на клиенте (см. «Историю
  трафика»). График показывает трафик по серверам, включая local exit, по
  sticky-правилам и по сетям назначения. Сеть подписана номером ASN и
  названием организации. Разрыв на графике означает, что клиент не работал.
  Живое окно хранится только в открытой вкладке и очищается при перезапуске
  клиента. При наведении на график показаны значения всех серий в этой точке.
  Цвет сервера одинаков на любом диапазоне.
- Компактная таблица серверов; вес, адрес, накопительные счётчики и последняя
  причина сбоя раскрываются в подробностях.
- Sticky-правила в порядке first-match: селектор, разрешённые выходы, текущий
  владелец, соединения и RX/TX. Local показывается явно; число resolved IP
  относится только к доменным правилам. Трафик без sticky-правила идёт в Fallback.
- Соединения: поиск по адресу/порту, фильтры протокола и выхода, по 50 строк на
  страницу. «Pause» замораживает только таблицу, сводка остаётся живой.
- Ресурсы процесса `svpn`: RSS, CPU в процентах одного ядра, накопительное
  user+system CPU time, число логических CPU и uptime. Текущий RSS читается из
  `/proc/self/status` на Linux; если он недоступен, показывается явно помеченный
  peak RSS из `getrusage`. Процент CPU считается в браузере по двум свежим
  снимкам из накопительного счётчика: при рестарте, разрыве API или устаревших
  данных выводится «—», а не выдуманное среднее. Значение больше 100% означает
  многопоточную нагрузку, а не ошибку.
- **Where traffic goes** показывает один и тот же объём внутренних IP-пакетов тремя способами: через какой выход они прошли (включая local), какой сети назначения (ASN) принадлежат и на какой IP направлены. *Since start* — объём с запуска, включая закрытые потоки; *Right now* — скорость за последний интервал измерения hub в Мбит/с. Сортировка и доли — по RX+TX, только приёму или только отправке. Нажатие на имя открывает текущие потоки, а не историю закрытых соединений.
- ASN фиксируется при открытии потока; без совпадения в базе — *Unknown ASN*. В снимке не больше 256 именных IP и 256 ASN на период. Мелкие группы объединяются в *Other · pooled*: общий расход точный, у именной строки могут отсутствовать байты, ранее вытесненные в остаток. Учёт только в памяти, до перезапуска клиента.
- Интерфейс: тёмная тема с мягким свечением и полупрозрачными карточками.
  Один акцентный цвет отмечает активный пункт меню, выбранный элемент и
  фокус. Остальные цвета показывают статус, направление приёма и отправки и
  серию трафика. Цвет сервера одинаковый в графике, в легенде, в полосах и в
  таблицах. Текст набран системным шрифтом. Моноширинный шрифт остался для
  адресов, портов и селекторов. Первый ряд страницы — плитки с крупными
  числами, за ними график на всю ширину. В шапке показаны серверы пула:
  состояние, транспорт и задержка. Тема следует системной, пока не выбрана
  своя. Выбор темы хранится только в открытой вкладке. `/` ставит курсор в
  поиск потоков. `Esc` сбрасывает поиск. *Clear filters* сбрасывает поиск,
  фильтры и переход из explorera. Внешних шрифтов, картинок и CDN нет: иконки
  встроены в страницу как SVG. Анимация отключается при
  `prefers-reduced-motion`.
- Состояния job'ов, последняя успешная попытка, причина ошибки и следующий запуск;
  для ASN/Country — загрузка в текущий процесс, число диапазонов и результат
  обновления. При неудаче прежняя таблица сохраняется. Ненулевой exit `run_if`
  означает пропуск; ошибка запуска проверки или её таймаут — неудачную попытку,
  видимую в статусе job, ошибке обновления базы и соответствующем счётчике.
- **Pinned groups** находятся в «Rules & exits», под таблицей правил. Блок
  показывает, на каком выходе закреплена каждая группа. ASN-группа подписана
  названием организации из ASN-базы, например «AS16509 · Amazon.com, Inc.».
  Выход показан именем сервера и его цветом. Группы отсортированы по трафику с
  запуска. Блок свёрнут: в заголовке видно только число групп. Щелчок по
  заголовку раскрывает список. В *Destination networks* у сети показаны цвет и
  имя её выхода. Технические счётчики остаются в раскрываемой диагностике.

Байты правил считаются с запуска клиента: TX — полный внутренний IP-пакет,
принятый очередью hub, RX — пакет, записанный в клиентский TUN. Это не подтверждение
доставки удалённому приложению. Переполненная очередь, отклонённый пакет и ошибка
записи не прибавляют байты. Правило закрепляется при открытии flow: DNS refresh
не переклассифицирует живое соединение, закрытие и reconnect не обнуляют totals.
Этот учёт включает local exit, в отличие от графика VPN-пула.

При потере API или неизменном снимке дольше пяти секунд экран явно помечается
устаревшим; скорость и живые RSS/CPU становятся неизвестными, а не нулевыми.
Возврат к живым данным не рисует вымышленную скорость за пропущенный интервал.
Накопительное CPU time и uptime основаны на последнем известном запуске и не
являются доказательством того, что процесс отвечает сейчас. Накопительные
счётчики подписаны «с запуска», свежие ошибки/drops показываются отдельно.

Серверы показывают настроенный список `mimic`; пустой список обозначен `Auto`,
это конфигурация, а не результат выбора текущей транспортной сессии.
Для IP назначения каждого flow показываются страна и ASN из загруженных таблиц
(независимо от правила/выхода), с отдельными фильтрами и поиском по организации.
Если таблицы нет или IP в ней не найден, значение — `Unknown`.
Пауза фиксирует строки, Geo-метаданные, названия активных ASN и варианты фильтров.

Названия организаций из четвёртой колонки DB-IP CSV разбираются и кешируются
**только в браузере**. При первом открытии видимой вкладки CSV загружается один
раз; `ASN names` / `Reload` позволяет загрузить или перечитать
его явно. Для текущей базы это около 29 MiB трафика через SSH-туннель. Роутер
только потоково читает файл блоками по 16 KiB, без словаря имён и без полного
CSV-буфера в процессе. На клиентском устройстве нужен современный браузер с
Fetch Streams; никаких запросов к DB-IP или другим внешним сайтам нет.
Через пять минут в скрытой вкладке полный словарь освобождается; для повторной
загрузки нажмите кнопку. При паузе сохраняются лишь имена ASN замороженных
строк, не весь словарь. Закрытие вкладки освобождает всё.
Ошибки загрузки не мешают JSON-снимкам, числовым ASN и фильтрам. База без колонки
названий также пригодна для маршрутизации; названия в ней недоступны.
После обновления CSV нажмите `Reload`, чтобы перечитать имена.

Адреса:

- `http://127.0.0.1:8080/` — страница с таблицами (обновляется раз в секунду);
- `http://127.0.0.1:8080/api/state` — снимок в JSON: у серверов `mimic`, у flow
  `country` / `asn` (nullable), но без словаря организаций; поле `history`
  говорит, включена ли история и как себя чувствует её база;
- `http://127.0.0.1:8080/api/history?range=24h&kind=link` — окно истории в JSON
  (`range=1h|24h|7d|30d` до текущего момента или `from=<unix>&to=<unix>` —
  любой период до 30 дней); `503` с причиной, пока истории нет или база в
  ошибке;
- `http://127.0.0.1:8080/api/asn.csv` — только настроенный CSV загруженной ASN-базы
  для браузерного парсера, без выбора произвольного пути. Ограничение — 128 MiB
  и 120 секунд на передачу; заголовок и простаивающая запись ограничены 3 секундами.
  До 8 HTTP-клиентов обслуживаются параллельно; медленная передача CSV не блокирует
  обычные JSON-снимки, при shutdown все подключения отменяются.

Морда только читает: править маршруты или sticky-группы из неё нельзя.
Адрес вне loopback запрещён — клиент откажется слушать, а не станет
открытым в сеть. На роутере доставайте её через SSH-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 root@router
```

и откройте `http://127.0.0.1:8080/` в локальном браузере.

Страница и JS-модули встроены в бинарь: npm, CDN, внешние шрифты и сервисы не нужны.
Проверки dashboard без npm-зависимостей:

```bash
node --test e2e/test_dashboard.mjs
node e2e/test_dashboard_browser.mjs
# Необязательно: сохранить desktop/mobile рендеры
DASHBOARD_SCREENSHOTS=/tmp/svpn-dashboard-preview node e2e/test_dashboard_browser.mjs
```

Браузерная проверка требует установленный Chrome; путь можно задать через `CHROME`.
В CI она запускается на Linux. Статическая fixture-морда и её управляющие endpoints
существуют только внутри self-check, в SVPN их нет.

## История трафика

График на морде помнит пять минут. Чтобы смотреть дальше, клиент раз в минуту
записывает те же счётчики в SQLite на клиенте:

```hcl
stats {
  db = "/var/lib/svpn/stats.sqlite"
}
```

Без конфига — флаг `--stats-db FILE`. Каталог создаётся, если его нет; без
блока и флага история не пишется. База нужна только на клиенте: ни сервера, ни
экспорта.

Что хранится, по минутам во времени UTC:

| Ряд | Ключ | Метрики |
| --- | --- | --- |
| сервер | `host:port` | байты и пакеты RX/TX, открыто, закрыто, ошибок открытия, дропов, активных потоков |
| local exit | — | то же |
| правило | сервер × sticky-правило; `fallback` для трафика без правила | байты RX/TX, активные потоки |
| сеть | ASN × сервер, 20 самых нагруженных за минуту | байты RX/TX, активные потоки |

Сервер и local exit получают строку каждую минуту работы клиента, правило и
сеть — только за минуту с трафиком. Поэтому пропуск без строк — это
остановленный клиент, а не нулевой трафик. Это внутренний IP-трафик, как и
вся морда: не весь WAN.

Три уровня: минуты хранятся сутки, свёрнутые из них часы — неделю, свёрнутые
из часов дни — 30 дней. Для трёх серверов и пары десятков сетей это около
2 МБ за месяц при пике журнала в 4 МБ. Если основной файл дорастает до 16 МБ,
клиент пишет предупреждение в лог и урезает хранение — сначала минуты старше
двух часов, затем часы и дни.

Ошибки базы не трогают VPN. Хаб отдаёт минуту в отдельный поток через
неблокирующую очередь и не ждёт диска. Сбой записи логируется не чаще раза в
10 минут, минуты копятся до двух часов и дописываются, когда база снова
доступна; ошибка видна в разделе Traffic и в поле `history` снимка. При
старте файл проверяется целостностью `integrity_check`: повреждённый файл
читается построчно, и что читается, переносится в новый файл; не читается
ничего — файл удаляется и заводится заново. Журнал после сбоя (файл `-wal`)
докатывается сам. Ошибка каталога или полный диск — не повреждение: файл
остаётся на месте, статус показывает причину, попытки повторяются.

Раздел **Traffic** читает из базы диапазоны длиннее пяти минут. Для этого он
запрашивает `GET /api/history`. Период задают
`range=1h`, `24h`, `7d` или `30d` — окно до текущего момента, — либо
`from=<unix>&to=<unix>` — любое окно до 30 дней. Уровень зависит от возраста
начала окна, потому что дольше уровня не хранится: до суток (с допуском в
четверть часа) — минуты, до недели — часы, дальше — дни. Подпись под графиком
говорит, какая ширина у точки. Остальные поля: `kind` — `link` (серверы и
local exit), `rule` или `network`; необязательные `top` (сколько рядов вернуть,
до 32, по умолчанию 8) и `link` (один сервер или `local`). Ряд не превышает
400 точек: сутки рисуются четырёхминутными интервалами.

В разделе есть и свои периоды. *Yesterday* одним нажатием показывает весь
вчерашний день по календарю браузера. *Custom…* открывает два поля даты и
времени и кнопку Apply (работает и Enter): окно открывается на последних
сутках и проверяется на месте — конец после начала, не больше 30 дней. Окно,
которое не доходит до «сейчас», само не обновляется; остальные график
перечитывает раз в минуту, пока он на экране.

Сети подписаны названием организации из той же ASN-базы, что обслуживает
морда. История читает CSV одним проходом, когда появляется сеть без имени, и
хранит имена у себя: на графике расшифровка есть и до загрузки словаря в
браузер, и после того как он освобождён. Словарь браузера остаётся запасным
источником. Без ASN-базы сети показываются номером.

## Только часть функций

Только sticky по именам, без баз:

```hcl
server "nl" { address = "203.0.113.10" }

sticky "claude" {
  names = ["claude.ai"]
  via   = ["nl"]
  every = "5m"
}
```

Только ASN-группы (автоматический sticky для всего):

```hcl
geo { db = "/etc/svpn/asn.csv" }

fallback_sticky {
  strategy = "sticky-asn"
}

server "nl" { address = "203.0.113.10" }
server "de" { address = "198.51.100.20" }
```

Только локальный egress по именам:

```hcl
server "nl" { address = "203.0.113.10" }

sticky "home" {
  names = ["printer.lan", "nas.home"]
  via   = local
  every = "5m"
}
```

`countries`-селекторам нужен `country.db`; `asn`-селекторам и
`strategy = "sticky-asn"` — `geo.db`. Не добавляйте в конфиг блоки, которые
не нужны вашему сценарию.

## Ограничения

- Туннелируется только IPv4. IPv6 не защищается этим конфигом.
- DNS SVPN не перехватывает. Исключение — режим `dns { mode = "exit" }`, см.
  «DNS за выходом». Системный резолвер остаётся вашим; SVPN сам разрешает
  только имена из sticky-блоков.
- Имя за большим CDN резолвится в тысячи адресов, общих с другими сервисами:
  sticky-группа «цепляет» и их, пока записи не вымоются. Для точечных случаев
  используйте `ips`.
- Полный Linux-пример использует TUN, root, `iproute2` и `nftables`.
- При `SIGKILL` клиентские hooks не выполняются. TUN и сокеты закрывает ядро.
  Следующий запуск должен восстановить свои маршруты и правила. Не используйте
  hooks для чужих необратимых изменений.
